= Chapter 5: Network Fundamentals and Application Flow Troubleshooting

== Learning Objectives

By the end of this chapter, you will be able to:

. Trace Layer 2 switching frames (MAC learning, VLAN segmentation, 802.1Q trunking) and Layer 3 packet forwarding paths (IP routing, ARP resolution, longest-prefix matching).
. Differentiate Layer 4 transport behaviors (TCP connection handshakes vs UDP connectionless streams) and identify standard automation port values.
. Diagnose the operational impact of core network services (DNS, DHCP, NTP) and edge devices (Firewalls, Load Balancers, NAT) on application traffic.
. Distinguish between the Management, Control, and Data planes of a modern network architecture.
. Identify and quantify the impacts of physical and logical network constraints (bandwidth, latency, jitter, packet loss) on software execution.

== 5.1 Introduction: When the Script Works Locally But Fails in Production

An automation engineer tests a Python script locally on their workstation and it completes in 1.5 seconds. When deployed to execute across an enterprise WAN, the script times out, drops API connections unpredictably, and fails with socket errors. The developer blames the network; the network engineer insists ping works.

Automation scripts depend on switching, routing, stateful firewalls, DNS lookups, and TCP transport dynamics. Understanding end-to-end packet flow is essential for diagnosing distributed automation failures.

Switches inspect ingress frames, populate their MAC address table with source MACs, and forward frames based on destination MAC addresses. If a destination is unknown, the frame is flooded out all ports in the same VLAN.

== 5.3 Layer 3 Forwarding: Routing, Subnets, and ARP

image::ch05/g5-3-router-forwarding-longest-prefix.png[Router Forwarding Decision and Longest-Prefix Match]

Routers decrement Time-to-Live (TTL), evaluate the destination IP against their routing table using **longest-prefix match**, resolve the next-hop MAC via ARP, and rewrite Layer 2 headers.

== 5.4 Layer 4 Transport: TCP, UDP, and Port Allocation

image::ch05/g5-4-tcp-three-way-handshake.png[TCP Three-Way Handshake and Connection Teardown]

=== Critical Automation Port Numbers
* **SSH (CLI):** TCP 22
* **DNS:** UDP/TCP 53
* **HTTP / HTTPS:** TCP 80 / 443
* **NETCONF over SSH:** TCP 830
* **NTP:** UDP 123

image::ch05/g5-6-firewall-nat-loadbalancer.png[Operational Function of Stateful Firewalls, NAT, and Load Balancers]

* **Stateful Firewalls:** Track connection state; permit outbound client requests and matching inbound replies while blocking unsolicited inbound connections.
* **NAT / PAT:** Translates private RFC 1918 IPs to public IPs, requiring reverse proxy configurations for inbound webhooks.
* **Load Balancers:** Terminate TLS and distribute API traffic across backend compute nodes.

== 5.6 Management, Control, and Data Planes

image::ch05/g5-7-network-planes-separation.png[Separation of Management, Control, and Data Planes]

* **Data Plane:** High-speed ASIC hardware forwarding customer packets.
* **Control Plane:** Routing protocols (OSPF, BGP) calculating path topologies.
* **Management Plane:** Administrative access via SSH, SNMP, RESTCONF, and NETCONF.

== 5.10 Key Terms

longest-prefix match:: Routing algorithm selecting the route entry with the most specific subnet mask matching the destination IP.
three-way handshake:: The initial TCP exchange (SYN, SYN-ACK, ACK) establishing a reliable transport session.
Control Plane:: Networking subsystem responsible for exchanging routing protocols and calculating path forwarding tables.
Data Plane:: Hardware subsystem responsible for forwarding packets from ingress to egress interfaces at line rate.
